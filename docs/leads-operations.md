# База заявок: эксплуатация

Серверный контур формы: PHP 8.0, MySQL `a250227_trexgo`, приватный конфиг вне
`httpdocs`. Этот файл — инструкция по развёртыванию и обслуживанию. Секретов здесь нет.

## Что лежит в репозитории

| Путь | Назначение |
|---|---|
| `api/leads.php` | `POST /api/leads`, приём заявки или подписки |
| `api/config.example.php` | форма приватного конфига без значений секретов |
| `db/migrations/` | пронумерованные миграции MySQL |
| `ops/migrate.php` | применение ещё не выполненных миграций |
| `ops/export_csv.php` | экспорт `leads` или `subscriptions` в приватную папку |
| `ops/backup_db.php` | сжатый `mysqldump` в приватную папку |
| `ops/cleanup_rate_limit.php` | удаление старых окон rate limit |
| `ops/sync_yandex_disk.php` | синхронизация MySQL ↔ `TrexGo — заявки.xlsx` |

Каталоги `db/`, `ops/`, `tests/` и внутренности `api/` закрыты собственными
`.htaccess`, в том числе в превью. Снаружи доступен только обработчик формы.

## Первый запуск

1. Сменить засвеченный пароль базы в панели Макхоста. Финальное подтверждение смены
   пароля делает владелец аккаунта.
2. Скопировать `api/config.example.php` в
   `/home/httpd/vhosts/trexgo.ru/private/leads-config.php`, заполнить значения и
   выставить права `0600`.
3. Сгенерировать отдельный ключ rate limit:

   ```bash
   php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"
   ```

4. Применить `db/migrations/001_create_leads.sql` через phpMyAdmin или один раз
   выполнить `ops/migrate.php` выбранным в панели PHP 8.0 CLI.
5. Проверить, что таблицы и соединение используют `utf8mb4`, а серверная сессия — UTC.
6. Отправить тестовую заявку. После проверки MySQL и обоих уведомлений подключить
   клиентские формы к относительному `api/leads`: так превью не пишет в боевую базу.

Настоящий конфиг не копируется в `httpdocs`, GitHub Secrets или репозиторий.

## Контракт API

Запрос — JSON, только с того же сайта. Обязательны:

- `request_id` — UUID v4, сохраняется для повторной отправки;
- `form_kind` — `lead` или `subscription`;
- `form_started_at` — Unix time начала заполнения, в секундах или миллисекундах;
- `phone` для заявки; телефон или `email` для подписки;
- пустое поле `website` — honeypot, пользователь его не видит.

Дополнительно принимаются имя, email, компания, комментарий, страница, referrer,
источник, UTM-поля и `yclid`. Телефон нормализуется до международного формата. Время
в MySQL хранится в UTC. Повторный `request_id` возвращает тот же `id` без новой строки
и без повторного уведомления.

Успех записи в MySQL возвращает `200`. Если база недоступна, но Telegram или письмо
приняли полные данные, возвращается `202`. Если не сработало ни одно хранилище,
возвращается `503` с телефоном и ссылкой WhatsApp. Телефон, email и комментарий в
технические логи не пишутся.

## Уведомления

В приватном конфиге задаются токен Telegram-бота, отрицательный `chat_id` группы,
адрес получателя и `From`. API всегда пытается отправить оба канала. Ошибка уведомлений
не превращает уже сохранённую в MySQL заявку в ошибку для посетителя.

## Слияние с веткой Метрики

Метрика и транспорт формы меняют один участок `script.js`, поэтому при слиянии нельзя
целиком выбирать одну из версий. Итоговый обработчик должен одновременно сохранить
цели Метрики и выполнить контракт API:

- endpoint — относительный `api/leads`, без ведущего `/`, чтобы превью не писало в прод;
- HTML-значение `data-form-kind="subscribe"` перед отправкой преобразуется в
  `form_kind: "subscription"`; `lead` передаётся без изменения;
- `form_started_at` и пустой honeypot `website` обязательны;
- запасной генератор `request_id` создаёт валидный UUID v4;
- успех признаётся только при HTTP 2xx и `result.ok === true`;
- UUID удаляется и цель Метрики отправляется только после подтверждённого успеха;
- при таймауте или ошибке UUID сохраняется для идемпотентного повтора;
- флаг отправки включается только после миграции, приватного конфига и сквозного теста.

Названия целей остаются в ветке Метрики и не задаются серверным кодом.

## CSV и резервные копии

Команды не печатают строки заявок в терминал; результат создаётся с правами `0600`
в каталогах из приватного конфига.

```bash
php ops/export_csv.php --table=leads
php ops/export_csv.php --table=subscriptions
php ops/backup_db.php
php ops/cleanup_rate_limit.php
```

Рекомендуемое расписание в панели Макхоста:

| Команда | Расписание |
|---|---|
| `sync_yandex_disk.php` | каждые 15 минут |
| `export_csv.php --table=leads` | ежедневно |
| `export_csv.php --table=subscriptions` | ежедневно |
| `backup_db.php` | ежедневно |
| `cleanup_rate_limit.php` | ежедневно |

**Путь к PHP CLI обязателен полным** — на Макхосте `php` без пути резолвится
в системный `/usr/bin/php` (5.6.37, не понимает `strict_types`/типизацию скрипта).
Рабочий бинарник — `/home/httpd/fcgi-bin/a250227_trexgo/php-cli` (PHP 8.1.21):

```bash
/home/httpd/fcgi-bin/a250227_trexgo/php-cli /home/httpd/vhosts/trexgo.ru/httpdocs/ops/sync_yandex_disk.php
```

**`error_log()` из CLI не попадает в `logs/error_log`.** Тот файл собирает только
ошибки FastCGI-обработчика веб-запросов; при запуске через `php-cli` PHP пишет
предупреждения и необработанные исключения в stderr процесса, а cron на Макхосте
никуда его не перенаправляет по умолчанию — значит фактически такие сообщения
пропадают. Диагностировано 16.08.2026 при разборе алерта «Синхронизация заявок
TrexGo не выполнена. Проверьте PHP error_log.»: сам текст алерта вводит в
заблуждение — `error_log` в этом случае пуст, даже если скрипт правда упал.
Чтобы видеть причину, добавить перенаправление stderr в отдельный файл прямо
в команде cron:

```bash
/home/httpd/fcgi-bin/a250227_trexgo/php-cli /home/httpd/vhosts/trexgo.ru/httpdocs/ops/sync_yandex_disk.php >> /home/httpd/vhosts/trexgo.ru/logs/sync_yandex_disk.log 2>&1
```

Путь к `mysqldump` тоже проверить на сервере до сохранения cron. Восстановление
из свежего дампа проверять раз в квартал на отдельной тестовой базе.

**Сеть до Яндекс.Диска с Макхоста периодически рвётся на уровне TCP** (curl отдаёт
HTTP 0, а не код ошибки API) — не баг синхронизации, а нестабильность сетевого пути
между хостами. Диагностировано 17.08.2026: прогон синхронизации 20 раз подряд дал
4 таких обрыва. Повторно подтверждено журналом 27.08.2026: встречаются как HTTP 0
на запросе API, так и обрыв скачивания XLSX. `YandexDiskClient` повторяет временные
 сетевые ошибки до 5 раз с паузами 4, 8, 16 и 32 секунды. Суммарное ожидание между
 попытками — 60 секунд: это снижает частоту запросов с Макхоста и остаётся внутри
 пятнадцатиминутного интервала cron. Ошибки авторизации и другие
постоянные ответы 4xx не повторяются. `trexgo_log_event('yandex_sync_failed', ...)`
пишет время, класс и подробную причину: искать её в `sync_yandex_disk.log`.

Алерт в Telegram/почту уходит не на первый сбой, а после
`TREXGO_SYNC_ALERT_THRESHOLD` (3) неудачных прогонов подряд — счётчик лежит в
`sys_get_temp_dir() . '/trexgo-leads-yandex-sync.failures'` и сбрасывается при
первом успешном прогоне. Так короткое сетевое окно недоступности не будит человека,
а по-настоящему сломанная синхронизация всё равно не остаётся незамеченной.

При ручной проверке через `for i in $(seq 1 15); do php-cli sync_yandex_disk.php; done`
без пауз между запусками Яндекс.Диск в ответ начинает отдавать HTTP 405 на каждый
запрос — это защита API от частых обращений, а не поломка. Гонять скрипт вручную
подряд без пауз не нужно: обычный cron с интервалом 15 минут в этот лимит не упирается.

## Таблица на Яндекс Диске

Файл — `TrexGo — заявки.xlsx`, два листа: `Заявки` (данные, читает скрипт) и
`Справка` (описание колонок и список статусов, скрипт не читает). Заголовок листа
`Заявки` нельзя переименовывать или переставлять руками в Excel — `XlsxLeadSheet::
read()` сверяет его строго и остановит синхронизацию при несовпадении. Менять
состав или порядок колонок можно только в коде (`XlsxLeadSheet::HEADERS`); после
такой правки старый файл на Диске несовместим — его нужно удалить, чтобы следующий
прогон создал новый с актуальной шапкой.

Колонки `Дата создания`, `Время создания` и `Дата контакта` — нативные ячейки
даты/времени Excel (работают фильтры, сортировка, форматирование), остальные —
текст. Даты в файле показываются по Москве, при записи в MySQL переводятся в UTC.

Скрипт сохраняет порядок существующих строк. Строка без `id` считается ручной заявкой,
получает UUID и добавляется в MySQL с `source = manual`, если источник не указан.
Удаление строки не удаляет заявку: на следующем прогоне она вернётся в конец. Для вывода
из работы используются статусы `lost` и `archived`.

Строка с некорректными данными (нечитаемый телефон/email у ручной заявки, статус не
из списка) не останавливает весь прогон. Такая строка пропускается на своём месте
(без `id`, если это новая заявка — подхватится после исправления), в Telegram и почту
уходит сообщение с номером строки и причиной, остальные строки синхронизируются как
обычно. Системные сбои (нет связи с Диском, обрыв соединения с MySQL, битая книга)
по-прежнему останавливают весь прогон.

Перед загрузкой скрипт повторно проверяет `modified`. Если файл менялся во время
прогона, новая версия не загружается, а в Telegram и почту уходит сообщение о конфликте.
Одновременный второй запуск блокируется файловой блокировкой.

## Проверки после развёртывания

- настоящий ли `REMOTE_ADDR` приходит за nginx;
- повтор одного `request_id` не создаёт вторую строку;
- UTM и `yclid` доходят без изменений;
- при недоступной базе заявка приходит в Telegram или по почте;
- в `error_log` нет телефона, email и комментария;
- ручная строка и изменение статуса проходят цикл XLSX → MySQL;
- конфликт `modified` отменяет загрузку и даёт уведомление;
- закрытые URL `/db/`, `/ops/`, `/tests/`, `/api/lib/` отвечают `403`.
