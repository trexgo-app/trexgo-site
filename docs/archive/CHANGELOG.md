## 2026-08-28 (4)

**Ревью PR #8 нашло дыру в самом gate — тоже закрыто до слияния.** Проверки
из записи ниже сами оказались обходимы: `grep -q` без якоря пропускал бы
`# AuthUserFile ...` (закомментированную строку) как «активную», а поиск
строки-маркера stage-заглушки внутри `api/leads.php` — как «настоящую
заглушку», даже если файл на самом деле боевой обработчик с этой строкой
внутри комментария. Заменено на: якорный regex (`^[[:space:]]*AuthUserFile`
и т.д. — директива должна реально начинать строку) для `.htaccess`; полное
совпадение `sha256` с эталонным хешем заглушки, захардкоженным в самом
`pull-deploy.sh`, для `api/leads.php` — этот файл неуязвим к правке
фиче-ветки, так как требует отдельной ручной укладки на сервер. Отдельно:
`stage.yml` теперь получает SHA нужного коммита через GitHub API до вызова
`deployhook.php` и после выкладки сверяет его с `stage-meta.json` — раньше
зелёный workflow подтверждал только «stage отвечает как положено», не «выложен
именно этот push».

## 2026-08-28 (3)

**Ревью PR #8 нашёл дыру в самом fail-closed сценарии — закрыто до слияния.**
Независимая проверка PR со сборкой stage во временной папке (см. запись ниже)
указала: до финального `rsync --delete "$FINAL/" "$TARGET/"` скрипт проверял
только наличие каталога `ops/stage-overlay`, а не содержимое результата —
пустой `htaccess-append`, откатанная заглушка `api/leads.php` или
переименованные метки Метрики ушли бы в `TARGET` незамеченными, и проверки
`stage.yml` увидели бы это только после публикации, ничего не откатывая.
Добавлен gate непосредственно перед финальным `rsync`: `.htaccess` содержит
`AuthUserFile`/`Require valid-user`, `robots.txt` — ровно `Disallow: /`,
`api/leads.php` отдаёт `"stored":"stage-stub"`, ни в одном `*.html` не осталось
`mc.yandex.ru`/`111364095`/`Yandex.Metrika`. Любое несовпадение останавливает
выкладку до того, как `TARGET` тронут.

## 2026-08-28 (2)

**Независимое ревью нашло окно без пароля на stage — закрыто.** До правки
`pull-deploy.sh` при `DEPLOY_ENV=stage` сначала раскладывал боевое дерево прямо
в `TARGET`, потом накладывал оверлей — между этими шагами (и особенно при
обрыве между ними) stage мог отдавать боевой сайт без Basic Auth и с рабочей
формой. Теперь оверлей накладывается на копию во временной папке, и в `TARGET`
уходит одним `rsync` уже готовый результат. Заодно: боевая Яндекс.Метрика
(счётчик `111364095`) вырезается из HTML на stage — раньше просмотры и тестовые
заявки со stage писались в боевую аналитику; `stage.yml` проверяет, что
`api/leads` на stage отвечает заглушкой, а не боевым обработчиком; в
`pull-deploy.sh` добавлен `flock` от повторной выкладки одного окружения по
переигранному вебхуку; в `stage.yml` убрана хрупкая передача curl-флагов через
word-splitting.

Правку `pull-deploy.sh` пришлось один раз уложить на сервер вручную по SFTP
(`temp/_deploy_pull-deploy_fix.py`, тот же приём, что при переходе на self-pull) —
self-pull запускает уже лежащий на диске скрипт и новую версию себя самого
не подхватывает. При первой попытке всплыл ещё один баг, не найденный
локально: bash на сервере — 4.1, `"${dry[@]}"` на пустом массиве под `set -u`
там падает с «unbound variable» (на bash ≥ 4.4 и локально — работает).
Исправлено на `"${dry[@]+"${dry[@]}"}"`, проверено тестовым сниппетом прямо
на сервере, затем полным прогоном `stage.yml`.
