# Лендинг TrexGo — состояние проекта

Статический сайт продукта: ЭТрН/ЭПЛ, тарифы, форма заявки, блог.
HTML/CSS/JS без фреймворка и сборки.

## Адреса

| Адрес | Что это |
|---|---|
| `trexgo.ru` | **боевой сайт**, хостинг Макхост |
| `trexgo.app` | старый адрес на Vercel — отдаёт `301` на `trexgo.ru`, см. ниже |
| `lk.trexgo.ru` | личный кабинет, планируется, отдельный репозиторий `trexgo-lk` |

## Как обновляется сайт

```
1. Ветка под задачу     git switch -c site-menu-perevozchiki
2. Правки, отправка     git push -u origin site-menu-perevozchiki
                        → stage.trexgo.ru обновился сам
3. Посмотрели вдвоём    https://stage.trexgo.ru/ (Basic Auth, доступ в GitHub Secrets)
4. Слили в main         боевой сайт обновился сам за ~30 секунд
5. Удалили ветку        не обязательно — stage просто перезапишется следующим push
```

Push в `main` запускает [.github/workflows/deploy.yml](../.github/workflows/deploy.yml).
Вручную ничего запускать не нужно.

**Файлы с раннера не заливаются — код с GitHub забирает сам сервер.** Actions
подписывает запрос общим секретом и дёргает `deployhook.php`; тот запускает
[ops/pull-deploy.sh](../ops/pull-deploy.sh), который скачивает архив репозитория
с `api.github.com`, проверяет его целостность и раскладывает `rsync`-ом.
Почему так, а не по FTP — в шапке самого скрипта.

Есть ручной запуск с галкой «холостой прогон»: Actions → Выкладка сайта на хостинг →
Run workflow. Показывает, что изменилось бы, ничего не трогая.

**Репозиторий — источник правды.** Правки прямо на хостинге затрутся при следующей
выкладке. Для production `rsync` идёт **без `--delete`**: файл, удалённый из
репозитория, на сервере остаётся и убирается руками. Так сохраняются файл
подтверждения прав для Яндекса и служебные файлы хостера, которых в репозитории
нет и быть не должно. Для stage `--delete` включён — там нет ничего постороннего,
содержимое должно точно совпадать с репозиторием плюс `ops/stage-overlay/`
(см. «Stage» ниже).

Не заливаются: `.github/`, `.claude/`, `CLAUDE.md`, `README.md`, `AGENTS.md`,
`docs/`, `config-snapshots/`, `temp/`, `vercel.json`, служебные файлы. Список
живёт в одном месте — в `ops/pull-deploy.sh`.

Настройка: секция `deploy` в `private/leads-config.php` (образец —
`api/config.example.php`) и секрет `DEPLOY_SECRET` в репозитории тем же значением.

## Локальный просмотр

Правки смотрим у себя, **до** пуша. Сайт статический, без сборки — достаточно
файлового сервера из папки `site/`:

```bash
python -m http.server 8000
```

Дальше `http://127.0.0.1:8000/`. Правим файл → `Ctrl+F5` в браузере → видим результат.
Остановить — `Ctrl+C`.

Альтернатива без команд: расширение **Live Server** в VS Code — правая кнопка по
`index.html` → Open with Live Server. Само перезагружает страницу при сохранении.

**Открывать `index.html` двойным кликом не годится.** Через `file://` не работает
Метрика, иначе ведут себя относительные пути и часть правил безопасности браузера.
Расхождение видно не всегда — тем оно и опасно.

**Что локально не проверяется:**

- `.htaccess` — локальный сервер не Apache, редиректы и блокировки не отработают;
- всё из списка «чего stage не показывает» (`../rules/stage.md`);
- поведение боевого домена: кэш, сертификат, ТСПУ.

Локальный сервер и stage не заменяют друг друга: первый — для себя в процессе
работы, второй — чтобы показать второму участнику.

## Stage

Push в любую ветку **кроме** `main` (а также ручной запуск с произвольным `ref`)
выкладывает эту ветку целиком на:

```
https://stage.trexgo.ru/
```

Логин и пароль (Basic Auth) — в GitHub Secrets `STAGE_AUTH_USER`/`STAGE_AUTH_PASSWORD`,
хеш лежит на сервере в `private/stage.htpasswd`, права `644`. Именно `644`, не `600`:
Apache на этом хостинге работает от пользователя `apache` (uid 48, группы
`apache`+`psaserv`), а не от пользователя сайта — в группу `psacln`, которой
принадлежит `private/`, он не входит, и `chgrp` в неё нашему аккаунту запрещён
(`Operation not permitted`). При `600` `mod_authn_file` не может прочитать файл
и отдаёт 401 при любом пароле, что и произошло при первой выкладке 28.08.2026.
Секрета в файле это не создаёт — там только apr1-хеш, а сам файл лежит вне
веб-корня. Один stage на весь проект, не по
одному на ветку — вторая ветка, запушенная позже, перезапишет предыдущую выкладку.
Это осознанный компромисс: два человека и несколько задач в неделю не создают
очереди, а нужно им показать друг другу — как правило, что-то одно за раз.

Собирает [.github/workflows/stage.yml](../.github/workflows/stage.yml) —
тот же паттерн HMAC-подписи и `pull-deploy.sh`, что у `deploy.yml`, только
с `env: stage` в теле запроса и другим `DEPLOY_TARGET` на сервере
(`subdomains/stage/httpdocs`).

Отличия stage от production применяются оверлеем `ops/stage-overlay/` — с
28.08.2026 (после находки ниже) не поверх уже разложенного в `TARGET` дерева,
а во временной папке рядом, и в `TARGET` уходит одним `rsync` уже готовый
результат. Сам `pull-deploy.sh` при `DEPLOY_ENV=stage`:

- заменяет `robots.txt` на `Disallow: /` целиком;
- дописывает в `.htaccess` `X-Robots-Tag: noindex` и Basic Auth (`Require valid-user`,
  доступно с Apache 2.1 — работает и на 2.2, и на 2.4);
- подменяет `api/leads.php` заглушкой, отвечающей `200 {"ok":true,"stored":"stage-stub"}`
  без обращения к боевой базе и без уведомлений в Telegram/почту — форма на stage
  не должна писать в те же таблицы, что production;
- вырезает из всех `*.html` блок Яндекс.Метрики целиком (между метками
  `<!-- Yandex.Metrika counter -->` и `<!-- /Yandex.Metrika counter -->`) —
  иначе просмотры и клики на stage, включая тестовые отправки формы через
  `reachGoal`, писались в боевой счётчик `111364095`; второй счётчик ради
  тестового трафика заводить не стали;
- добавляет плашку `stage-badge.js` в угол экрана (метаданные — `stage-meta.json`,
  пишется при каждой выкладке).

Basic Auth — единственная настоящая защита; `noindex`-заголовок и `robots.txt`
только гигиена на случай прямой ссылки.

**Почему сборка во временной папке, а не оверлей поверх `TARGET`.** До
28.08.2026 `rsync` сначала клал в `TARGET` боевое дерево (настоящий
`api/leads.php`, `.htaccess` без пароля, боевую Метрику), и только следующим
шагом скрипта поверх накладывался оверлей. Между этими шагами — секунды на
реальной передаче — stage отдавал боевой сайт без пароля и с рабочей формой;
при обрыве ровно между ними это состояние могло задержаться надолго. Сейчас
`pull-deploy.sh` собирает итог (`rsync` + оверлей) в `$WORK/final` и только
потом одним `rsync --delete` переносит готовое в `TARGET` — `.htaccess`,
попадающий в `TARGET`, уже содержит Basic Auth с первого байта.

**Файл-замок от повторного вебхука.** `deployhook.php` принимает подписанный
запрос в течение 300 секунд после `ts` — в этом окне его можно переслать
повторно в обход GitHub Actions (`concurrency` в workflow здесь не защита:
она работает только для запросов, прошедших через сам Actions). `pull-deploy.sh`
берёт `flock` на `private/deploy-lock-<env>` перед началом работы; если замок
занят, вторая выкладка того же окружения завершается ошибкой, не начинаясь.

**Сведение нескольких веток.** Если нужно показать сразу несколько задач вместе —
одноразовая интеграционная ветка (`git switch -c integration main`, затем
`git merge --no-ff <ветка>` для каждой), запушенная как обычная ветка. После показа
удаляется и локально, и на origin — никогда не используется как база для новых веток.
Подробнее о терминах и цикле — [../rules/stage.md](../../rules/stage.md).

Почему поддомен, а не папка `/preview/`, как раньше — сертификат стал wildcard
(`*.trexgo.ru`), прежнее ограничение снято; исход решения — в
[archive/proposals/preview-varianty.md](archive/proposals/preview-varianty.md).

## Старый адрес `trexgo.app`

Vercel остался подключённым к этому репозиторию через GitHub App организации —
интеграцию при переезде не отключали. Поэтому push в `main` идёт в два места:
Actions заливает файлы на Макхост, Vercel параллельно собирает `trexgo.app`.

Чтобы старый адрес не был вторым живым сайтом, в корне лежит
[vercel.json](../vercel.json): любой путь отдаётся `301` на тот же путь
на `trexgo.ru`. `www.trexgo.app` привязан к тому же проекту и отдаёт `307`
на `trexgo.app` — то есть по цепочке из двух переходов приходит на боевой адрес.

Файл в выкладку на Макхост не попадает: он в списке исключений `EXCLUDE`
в [ops/pull-deploy.sh](../ops/pull-deploy.sh), общем для production и stage;
Apache его всё равно не читает.

Проверка после деплоя:

```bash
curl -sI https://trexgo.app/waybills.html | head -3
```

Ожидается `301` и `location: https://trexgo.ru/waybills.html`.

ТСПУ редиректу не мешает: у `301` нет тела, обрывается только отдача больших
страниц (см. ниже).

Домен зарегистрирован через Vercel на аккаунте Сергея, NS — `ns1/ns2.vercel-dns.com`.
**Продление домена — обязательное условие:** истечёт `trexgo.app` — редирект
исчезнет вместе с ним, и старые ссылки станут битыми.

## Почему уехали с Vercel

ТСПУ режет клиентские домены Vercel: соединение устанавливается, заголовки приходят,
а тело обрывается на ~21 КБ и висит до таймаута. Проверено на посторонних сайтах —
`resend.com`, `cal.com`, `linear.app` ведут себя так же. Собственные домены Vercel
(`vercel.com`, `nextjs.org`) при этом работают.

Смена IP внутри Vercel не помогает — фильтр следует за именем домена, а не за адресом.

На Макхосте та же картинка 1,09 МБ приходит целиком за 0,5 с.

## Структура сайта: две оси навигации

Продуктовая ось — что мы делаем: ЭТрН, путевые листы, AI-аналитика. Ролевая ось —
кому это нужно: раздел меню **«Кому подходит»**, выпадающий список без своей
страницы-хаба.

Разрез по ролям взят тот же, что в базе знаний (`knowledge/wiki/etrn/users/`) —
чтобы вики и сайт не разъезжались. Сейчас в разделе три страницы, новая роль
добавляется как ещё один пункт списка.

**В бургере выпадающего списка нет** — все пункты идут одним плоским рядом, ролевые
страницы вперемешку с продуктовыми. На узкой колонке заголовок «Кому подходит» ничего
не группировал, а ломал ряд лишним кеглем и отступом. Раскрывать там нечего, поэтому
кнопка-переключатель на этой ширине просто скрыта.

**Все три ролевые страницы открыты для индексации и есть в `sitemap.xml`** (01.08.2026).
`noindex` стоял, пока это были заглушки; снят после того, как тексты посмотрел второй.
У каждой страницы свой `canonical` на адрес с `.html` — тот, по которому она
реально отдаётся.

### Общие стили и скрипты ролевых лендингов

Три страницы раздела свёрстаны одинаково — общая шапка сайта, плавающее меню по
странице, hero с макетом телефона, карточки, чёрный блок дедлайна, мобильная плашка
с кнопкой. Общее вынесено в два файла в корне, а не продублировано трижды:

| Файл | Что внутри |
|---|---|
| `role-landing.css` | все классы `.pv-*`: плавающее меню, hero, анимации телефона, секции, адаптив |
| `role-landing.js` | счётчик дней до 01.09.2026, плавающее меню со скроллспаем, мобильная плашка, появление секций |

Подключаются только на этих трёх страницах, после `styles.css` и `script.js`
соответственно. Базовая типографика, кнопки, футер и FAQ живут в `styles.css`
и здесь не дублируются.

Каждый блок в `role-landing.js` сначала проверяет, есть ли его элементы на странице:
состав секций у лендингов разный. Анимация появления секций (`.pv-reveal`) прячет блок
только вместе с классом `js-reveal` на `<html>` — его ставит сам скрипт, так что без JS
секции видны сразу, а не остаются скрытыми навсегда.

### Две навигации на ролевых лендингах

Шапка у ролевых страниц **та же самая, что на остальном сайте** (`nav.nav` из `styles.css`) —
со своей шапкой они оставались единственными страницами без бургер-меню в адаптиве.
Навигация по разделам самой страницы вынесена в отдельный элемент `.pv-pagenav` —
таблетку, которая висит под шапкой:

- появляется, когда прокручен первый экран, и уходит на форме заявки — пока герой
  на виду, второй ряд меню только спорит с шапкой;
- активный раздел подсвечивается, под ним едет чёрный маркер; позицию и ширину маркера
  считает JS — CSS не умеет измерить ширину произвольной подписи;
- активным считается **последний раздел, чей верх прошёл линию в трети экрана**. Считаем
  по `scroll`, а не через `IntersectionObserver`: короткие разделы помещаются в экран
  вместе с соседями, и наблюдатель на них мигает между двумя пунктами;
- на мобильном таблетка тянется во всю ширину и скроллится горизонтально, активный пункт
  подтягивается в видимую часть; кнопка заявки в ней скрыта — внизу уже есть плашка.

Отсюда требование к подписям: **один пункт — одно-два слова**. Ряд из четырёх пунктов плюс
кнопка — потолок, при котором таблетка на десктопе помещается без прокрутки.

Плавный переход по якорю сдвигается на 160 px вместо обычных 80 (`script.js`): под шапкой
висит таблетка, и без запаса заголовок раздела уезжает под неё. Отличаются страницы
наличием `#pageNav`.

### Сетки в две колонки — класс `.split-2`

Блоки «было / стало» на `waybills.html` и «окупаемость» на `ai-analytics.html` стояли
инлайном жёсткими `grid-template-columns: 1fr 1fr` и на узком экране давали
горизонтальный скролл: колонка не схлопывалась. Теперь оба используют `.split-2`
из `styles.css` — две равные колонки, одна колонка ниже 768 px.

**Не заменять это на `auto-fit`.** При двух детях `repeat(auto-fit, minmax(...))`
создаёт на широком экране лишние пустые треки, и колонки не добирают ширину
контейнера: на 1280 px сетка выходила 1136 px вместо 1200. Медиа-запрос
предсказуемее.

Тем же порядком `.pricing-grid` переведена на `auto-fit` — но там карточек три
и пустых треков не возникает, а жёсткие три колонки давали скролл около 800 px.

## Что настроено в .htaccess

Редирект HTTP → HTTPS, `www` → без `www`, сжатие, кэш картинок на год,
`/favicon.ico` → `favicon.svg`, блокировка файлов, начинающихся с точки
(кроме `/.well-known/` — он нужен для продления сертификата).

## Проверка, что всё работает

```bash
# Страницы (пока DNS не везде доехал — через прямой IP)
curl -s --compressed -m 20 -o /dev/null --resolve "trexgo.ru:443:178.208.83.20" \
  -w "%{http_code} %{size_download}\n" https://trexgo.ru/

# Самая тяжёлая картинка — тест на ТСПУ, должна прийти целиком
curl -s --compressed -m 40 -o /dev/null --resolve "trexgo.ru:443:178.208.83.20" \
  -w "got=%{size_download} time=%{time_total}\n" https://trexgo.ru/Stati_image/1.webp

# Stage: без пароля 401, с паролем 200 и заголовок noindex
```

## Форма заявки и аналитика

Все блоки `.lead-form` отправляют JSON в `POST api/leads` (относительный путь, чтобы
stage не писал в прод). Тип берётся из `data-form-kind`; класс
`.inline-subscribe-form` — запасной признак подписки, если атрибут не проставлен.
Клиент создаёт UUID v4 запроса, добавляет пустой honeypot `website` и время начала
заполнения `form_started_at`, блокирует кнопку на время отправки, передаёт UTM и
`yclid`. Успехом считается только HTTP 2xx с `result.ok === true`; при ошибке или
таймауте UUID сохраняется для идемпотентного повтора, при успехе — удаляется.

Приватный конфиг, миграции MySQL и сквозной тест отправки выполнены — формы
на боевом сайте работают. Подробности API, антиспам, уведомления, резервные копии
и синхронизация с Яндекс Диском — в [leads-operations.md](leads-operations.md).

Счётчик Метрики — `111364095`, установлен на всех страницах. Цель `lead_submit_success`
для заявок и `subscription_submit_success` для подписок отправляется только после
подтверждённого сервером успеха. Клики по ссылкам `tel:` отправляют событие
`phone_click`, переходы в WhatsApp и Max — `messenger_click`. Эти микроцели не
заменяют подтверждённую заявку и не должны быть основной целью оптимизации Директа.

## Известные проблемы

**Картинки не пережаты** — 7,91 МБ в 15 файлах, самая тяжёлая 2,25 МБ.
На хостинге грузятся быстро, но на мобильном интернете это много. Есть imagick.

**Пароли засветились** в переписке в Telegram: FTP и база. Сменить после того,
как всё устоится, новые — в GitHub Secrets.

**Выкладка больше не ходит по FTP** — 28.08.2026 сайт переведён на ту же схему,
что кабинет: сервер сам забирает код с GitHub. FTP-пароль в выкладке не участвует
и по сети открытым текстом не ходит. Сменить его всё равно нужно (он засветился
в переписке), но это больше не блокирует деплой.
