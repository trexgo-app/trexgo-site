### Другие версии PHP и запуск из консоли

Снято 27.08.2026. Версия выше — та, что настроена для самого `trexgo.ru`;
у поддоменов она своя, задаётся отдельно (у `lk` — та же 8.1.21).

**В `/usr/bin` современного PHP нет:** `/usr/bin/php` — это **5.6**, каталоги
`php52…php73` заканчиваются на 7.3, а для 8.x лежат только CGI-бинарники
(`php-cgi8.0`…`php-cgi8.3`).

Правильный способ запуска — **обёртка хостера**, она же указана в справке панели:

```
/home/httpd/fcgi-bin/<ftp-логин>/php-cli /путь/к/скрипту.php >> /путь/к/логу 2>&1
```

Внутри это две строки на bash — вызов `/opt/alt/php81/usr/bin/php` с нашим
`php.ini` из `fcgi-bin/`. То есть **настоящий CLI SAPI, PHP 8.1.21**, и заодно
те же настройки PHP, что у сайта. Каталоги `/opt/alt/phpXX/` есть и для других
версий.

Если скрипт всё же зовут через `/usr/bin/php-cgi8.1 -q -f …`, он работает, но
ведёт себя иначе, и на все три отличия уже наступали при настройке продления
OAuth-токена кабинета:

- `PHP_SAPI` равен `cgi-fcgi`, а не `cli` — проверка на `'cli'` отвергнет
  собственную задачу. Веб-запрос отличать по `$_SERVER['REQUEST_METHOD']`;
- константы `STDOUT` и `STDERR` не определены — обращение к ним роняет скрипт
  фаталом. Выводить через `echo`;
- директива `error_log` пустая, сообщения уходят в stderr, то есть в никуда.
  Задавать свой файл через `ini_set('error_log', …)`.

Писать скрипты лучше так, чтобы шли под обоими: разница вскрывается не сразу,
а в первый запуск по расписанию.

Из полезного для кода: `curl` включён, `hash()` умеет `gost` и `gost-crypto`
(ГОСТ Р 34.11-94, в том числе вариант CryptoPro).

### Что придётся поправить, когда появится PHP-код

Сейчас сайт статический, но при добавлении формы заявки или кабинета это выстрелит:

- **`display_errors = Off`, `log_errors = On`** — ошибки не видны в браузере, искать их в
  `logs/error_log`. Это правильная настройка для боевого сервера, менять не нужно.
- **`default_charset = ""`** — пустая. PHP не будет сам ставить `charset=utf-8` в
  `Content-Type`, кириллица поедет. Указывать кодировку явно в коде или заголовках;
  в `.htaccess` уже стоит `AddDefaultCharset UTF-8` для статики.
- **`request_order = "GP"`** — в `$_REQUEST` попадают только GET и POST, куки нет.
- **`session.cookie_httponly`** пустая, **`session.cookie_secure`** не задана — при работе
  с сессиями выставлять флаги явно, иначе куку можно угнать через JS и она уйдёт по HTTP.
- **`expose_php = On`** — сервер сообщает версию PHP в заголовке `X-Powered-By`.
  Наружу сейчас не видно (nginx срезает), но при своей обработке PHP проверить.
- **`log_errors_max_len = 1024`** — длинные ошибки обрезаются в логе.

## Веб-сервер

Перед Apache стоит nginx — наружу отдаётся только `Server: nginx`.
**Версия Apache неизвестна:** хостер скрывает её и в заголовках, и в `phpinfo`,
и в панели. Поэтому все правила в `.htaccess` пишутся в синтаксисе,
совместимом с 2.2 и 2.4 (`RewriteRule ... [F,L]` вместо `Require all denied`).

Модули подтверждены косвенно, по работе: mod_rewrite, mod_deflate, mod_expires.

Панель хостинга — не Plesk, не ISPmanager, не cPanel: собственная разработка Макхоста.
Публичного API у неё нет, всё разовое делается руками через cp.mchost.ru.

| **SFTP, порт 22** | **работает**, OpenSSH 8.7, те же логин и пароль |

Отпечаток ключа хоста (RSA), проверять при первом подключении:

```
rtV6fnGKM/gwusoVZa5nKDnNO9f9e5lTqCuoyh6UC/o=
```

Ключ ed25519 сервер тоже отдаёт, но `libssh2` (на нём работает curl) его не поддерживает —
подключаться по RSA. В FileZilla и WinSCP это ограничение не действует.

Через SFTP виден весь путь `/home/httpd/vhosts/trexgo.ru/`, а не только корень сайта:
это тот же аккаунт, просто без chroot.

**SSH-shell работает** (проверено 27.08.2026, ранее здесь было записано обратное):
команды выполняются под `uid=23614(a250227_trexgo)`, доступны `ls`, `grep`, `tail`,
`curl`, запуск PHP. Ограничения всё же есть: `crontab` отвечает `Permission denied` —
задачи заводятся только через панель.

**Выкладка пока идёт по обычному FTP** — `FTP-Deploy-Action` умеет только его, а он даёт
инкрементальную синхронизацию (заливает лишь изменённые файлы). Цена — пароль ходит открытым
текстом. Переход на SFTP — отдельная задача, см. `docs/README.md`.

**FTP рвёт соединение при заливке подряд без пауз.** Измерено 28.08.2026 отдельным
скриптом на 25 файлах:

| Как заливаем | Результат |
|---|---|
| подряд, без пауз | обрыв на 16-м файле: `426 Transfer aborted. Interrupted system call` |
| с паузой 0,7 с | 25 из 25 за 96 с |
| переподключение каждые 10 файлов | 25 из 25 за 77 с |

Одиночная заливка и заливка крупного файла проходят всегда — дело в числе передач
подряд, не в объёме. `FTP-Deploy-Action` ни пауз, ни переподключения не умеет
(«This library does not currently handle reconnects»), поэтому **оборванный файл
остаётся на сервере нулевого размера**. Так дважды обнулился `.htaccess` кабинета.

Повтор выкладки после обрыва это не лечит: прогресса между подходами нет.
Поэтому 28.08.2026 оба репозитория ушли с FTP на схему «сервер сам забирает код
с GitHub» — раннер только дёргает `deployhook.php`. Обратное направление свободно:
сервер тянет весь репозиторий одним запросом к `api.github.com` за 0,7 с.
Разбор — в `ops/pull-deploy.sh`.

**SSH из Actions не проходит вовсе:** TCP-порт 22 открыт, но обмен ключами
замирает на `SSH2_MSG_KEX_ECDH_REPLY`. С нашей машины тот же ключ работает —
то есть хостинг фильтрует адреса раннеров. `lftp` с переподключениями упирается
в то же самое.

## Структура аккаунта

Полный путь: `/home/httpd/vhosts/trexgo.ru/`. По FTP видно то же самое от корня.

```
httpdocs/          корень сайта — сюда льёт GitHub Actions
  preview/         превью веток, заливает отдельный workflow
logs/              access_log, error_log, mail.log, eaccelerator_log
private/           вне веб-доступа: phpinfo, конфиги ЛК, токен и лог крона
subdomains/        lk/ (личный кабинет), lk-stage/, stage/
statistics/        отключена в панели
tmp/               сессии, загрузки, кэш
pd/, cgi-bin/
```

**Логи принадлежат пользователю `apache`** и нам недоступны на запись. Из PHP под
Apache записи через `error_log()` туда идут, из скриптов по расписанию — нет:
им нужен свой файл в `private/`.

Состояние поддоменов на 27.08.2026: код выложен только в `lk/httpdocs` (туда целится
деплой кабинета), `lk-stage/` и `stage/` заведены, но содержат лишь заглушку.

**Поддомен** заводится в панели и появляется как
`subdomains/<имя>/httpdocs` — отдельного FTP-логина у него нет, доступ через тот же аккаунт.
Отдельный FTP-доступ Макхост выдаёт на домен целиком, а не на поддомен.

### Что выкладка удаляет, а что нет

Проверено экспериментом 31.07.2026: `FTP-Deploy-Action` ведёт список залитых им файлов в
`httpdocs/.ftp-deploy-sync-state.json` и трогает **только их**. Посторонняя папка, созданная
руками, пережила выкладку без изменений (`Making changes to 0 files/folders`).

Поэтому `httpdocs/preview/` безопасно жить рядом: боевая выкладка её не сносит.
Обратное тоже верно — если что-то залить руками мимо гита, оно останется навсегда
и о нём никто не вспомнит.

Исключение — параметр `dangerous-clean-slate`: он стирает `server-dir` целиком, игнорируя
`exclude`. Не включать.
